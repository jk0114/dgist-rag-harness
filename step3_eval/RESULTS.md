# 검색(Retrieval) 평가 결과

`python -m step3_eval.run_eval`로 얻은 최신 결과 요약. 원본 데이터는 [`data/queries.json`](data/queries.json)(질의+정답),
[`data/hyde_cache.json`](data/hyde_cache.json)(HyDE 가상 문서), [`data/results/latest.json`](data/results/latest.json)(질의별 상세 결과)에 있다.

## 평가 방법

- **질의**: DGIST 연구실 232개 각각에 대해 `"{연구 분야}에 관심이 있는데 어떤 과목을 들으면 좋을까?"` 형태로 자동 생성.
- **정답(GT)**: 그 연구실이 실제로 추천하는 과목 목록(`extract_course_tree.py`가 학교 페이지에서 추출).
- **비교 대상**: `vanilla`(순정 dense 검색) / `vanilla+hyde` / `graph-rag`(키워드 그래프 재점수화) / `graph-rag+hyde`.
- **지표**: Precision@10·Recall@10·MRR·nDCG@10(모두 top-10 고정), MAP(전체 랭킹, K 무관). 이 데이터셋은 질의별 정답 개수 편차가 크므로(3~33개), **nDCG·MAP이 질의 간 비교에 가장 공정한 지표**다. 계산식은 [`run_eval.py`](run_eval.py)의 `metrics()`/`average_precision()`이 정의다.
- **검색 풀**: 청크 60개를 먼저 뽑은 뒤 과목 단위로 중복 제거해서 과목 랭킹으로 바꾸고, 그 상위 10개 과목으로 Precision/Recall/nDCG를 계산한다.

## 지표 설명

`retrieved`는 한 질의에 대해 모델이 뽑은 과목 랭킹(점수 내림차순), `relevant`는 GT 정답 과목 집합, `k=10`이다.
아래 다섯 지표 모두 [`run_eval.py`](run_eval.py)의 `metrics()`/`average_precision()`이 정의 그대로다.

### Precision@k — "상위 k개 중 몇 개가 정답인가"
```
precision = (상위 k개 중 정답 개수) / k
```
가장 직관적인 지표. 다만 이 데이터셋처럼 질의마다 정답 개수가 3~33개로 편차가 크면, 정답이 5개뿐인 질의는 Precision@10이 구조적으로 0.5를 못 넘어서 질의 간 비교가 불공정해진다.

### Recall@k — "전체 정답 중 몇 개를 상위 k개 안에서 찾았나"
```
recall = (상위 k개 중 정답 개수) / (전체 정답 개수)
```
Precision과 분모만 다르다(자른 개수 k 대신 전체 정답 개수). 정답이 30개인 질의는 상위 10개만 봐서는 Recall@10이 구조적으로 0.33을 못 넘는다 — Precision과 마찬가지로 질의별 정답 개수 편차에 취약하다.

### MRR (Mean Reciprocal Rank) — "정답을 얼마나 빨리 찾았나"
```
그 질의의 RR = 1 / (첫 번째로 나온 정답의 순위)   # 정답을 하나도 못 찾으면 0
MRR = 모든 질의의 RR 평균
```
상위 랭킹 중 **가장 먼저 등장한 정답 하나**의 위치만 본다. 예를 들어 1위가 정답이면 RR=1.0, 3위에서야 처음 정답이 나오면 RR=1/3. "사용자가 리스트를 위에서부터 몇 번째까지 봐야 쓸모있는 답을 만나는가"에 가까운 지표라, top-1 적중률과 강하게 연동된다(이 프로젝트에서 HyDE가 MRR을 깎아먹는 것도 top-1 적중률 하락이 직접 원인이었다).

### nDCG@k (normalized Discounted Cumulative Gain) — "정답이 상위에 몰려 있을수록 높은 점수"
```
DCG  = Σ (i번째가 정답이면 1, 아니면 0) / log2(i + 1)     # i = 1..k
IDCG = Σ 1 / log2(i + 1)                                  # i = 1..min(정답 개수, k) — 이론상 최댓값
nDCG = DCG / IDCG
```
정답이 몇 위에 있는지에 따라 `log2(순위+1)`로 점수를 깎는다(1위 정답과 10위 정답은 기여도가 다르다). **`IDCG`를 `min(정답 개수, k)`로 정규화**하는 게 핵심 — 이 덕분에 정답이 3개뿐인 질의든 30개인 질의든 이론적 최댓값이 항상 1.0이 되어서, Precision/Recall@k와 달리 **질의별 정답 개수 편차에서 자유롭다**.

### MAP (Mean Average Precision) — "랭킹 전체를 보고, 정답을 찾을 때마다의 정밀도를 평균"
```
그 질의의 AP = Σ (i번째가 정답이면, 그 순간까지의 precision) / (전체 정답 개수)   # i는 자르지 않은 전체 랭킹
MAP = 모든 질의의 AP 평균
```
k로 자르지 않고 랭킹 전체를 본다. 정답을 하나 찾을 때마다 "지금까지 본 것 중 정답 비율"을 기록해서 정답 개수로 나누기 때문에, 끝까지 못 찾은 정답은 자동으로 0점 취급되면서도 **정답 개수가 몇 개든 같은 잣대**로 비교된다.

nDCG@k와 MAP은 둘 다 질의별 정답 개수 편차 문제에서 자유로워서, 이 프로젝트에서는 이 둘을 **가장 신뢰할 수 있는 비교 지표**로 삼았다. Precision/Recall@k는 참고용으로만 본다.

| pipeline | Precision@k | Recall@k | MRR | nDCG@k | MAP |
|---|---|---|---|---|---|
| vanilla | 0.2504 | 0.1837 | 0.5249 | 0.2726 | 0.1602 |
| vanilla+hyde | 0.2534 | 0.1865 | 0.4822 | 0.2700 | 0.1679 |
| **graph-rag** | **0.2897** | **0.2155** | **0.5714** | **0.3177** | 0.2130 |

| vanilla | vanilla+hyde | graph-rag | graph-rag+hyde |
|---|---|---|---|
| 34.9% | 27.6% | **37.5%** | 29.3% |

## 관찰

**graph-rag가 전반적으로 가장 우수하다.** nDCG@k(0.318)와 MRR(0.571) 모두 4개 파이프라인 중 최고 — 코퍼스 안의 실제 키워드/구조 연결을 근거로 이웃 청크 점수를 끌어올리는 방식이 vanilla 대비 확실한 개선을 보인다.

**HyDE는 MRR을 오히려 낮춘다** (vanilla: 0.52→0.48, graph-rag: 0.57→0.49). 원인을 질의 단위로 추적해보면: HyDE가 질의 키워드에 정확히 맞춰 **아주 좁고 구체적인 가상 과목 하나**를 지어내는데(예: "유기금속촉매론"), 이게 임베딩을 그 특화 주제 쪽으로 확 당겨버려서, 정작 GT에 포함된 더 넓은 커리큘럼(기초 화학 과목 등)을 밀어낸다. 예:

> 질의: "유기화학, 유기금속화학, 촉매에 관심이 있는데..."
> - vanilla top-1: 유기화학Ⅰ (정답 ✓)
> - vanilla+hyde top-1: 유기금속화학 (정답 아님 ✗)
> - HyDE가 지어낸 문서: *"유기금속촉매론 ... organometallic catalysis, transition metal complexes..."*

MAP은 vanilla+hyde(0.168)가 vanilla(0.160)보다 소폭 높아서, "전체 랭킹 어딘가에는 정답이 더 들어있다"는 점에서 완전히 손해는 아니다 — 다만 1등을 맞추는 능력(MRR)은 떨어진다.

### 시도했다가 되돌린 것: HyDE 프롬프트를 "더 넓게" 쓰게 하기

가설: "가상 문서를 기초~응용을 아우르는 넓은 내용으로 쓰게 하면 HyDE의 좁은-특화 편향이 완화되지 않을까?" → **실제로는 vanilla+hyde의 5개 지표가 전부 더 나빠졌다** (MRR 0.482→0.471, nDCG 0.270→0.262, MAP 0.168→0.164).

이유로 추정되는 것: 코퍼스 안의 실제 문서(강의계획서)는 전부 "구체적인 과목 하나" 형태다. 가상 문서를 일부러 뭉뚱그려서 넓게 쓰면, 그 문서와 코퍼스 안의 특정 문서들(정답 포함) 사이의 유사도가 전반적으로 흐려진다 — 즉 "기초 과목도 챙기게 하려는" 의도가 "모든 과목과 애매하게 비슷한 흐릿한 벡터"를 만드는 부작용으로 이어졌다. 부수적으로 생성 언어도 한국어 비중이 82%→100%로 바뀌었는데(실제 강의계획서 교과개요는 영어인 경우도 많음), 이 역시 코퍼스 문체와의 괴리를 키웠을 수 있다. 이 프롬프트 변경은 되돌렸고, [`hyde.py`](../step2_retrieval/hyde.py)는 "행정 필드 제거" 버전만 유지한다.

**시사점**: 좁은 특화 과목과 넓은 기초 과목을 동시에 잘 맞추려면, 가상 문서 하나로는 구조적 한계가 있어 보인다 — 다음 시도로는 가상 문서를 여러 개(특화용 + 기초용) 만들어 검색 결과를 합치는 방식이 유력한 후보다.
